# Извлечение характеристик кандидатов КТРУ

Самостоятельный uv-проект. Его `.venv`, `pyproject.toml` и `uv.lock` не зависят
от окружения API и поиска. HTTP-сервис использует FastAPI/Uvicorn, разбор —
`pymorphy3` и русский словарь. Модели, PyTorch и корневой `search.py` не
импортируются в базовом режиме. Python 3.12+; тесты используют `unittest`
и HTTP-клиент из отдельной группы `dev`.

## Запуск HTTP-сервиса

Из корня репозитория:

```bash
cd chars_extractor
uv sync --locked --no-dev
uv run --no-dev uvicorn service:app --host 127.0.0.1 --port 8001 --reload
```

Основной backend может продолжать работать на `8000`; этот процесс слушает `8001`.
Остановка — `Ctrl+C`. Порт можно изменить аргументом `--port`.
Для доступа с других машин укажите `--host 0.0.0.0`; в URL клиента используйте
реальный адрес сервера. Без `--reload` запускается обычный процесс без
автоматического перезапуска при изменении исходников.

- Swagger UI: <http://127.0.0.1:8001/docs>
- ReDoc: <http://127.0.0.1:8001/redoc>
- OpenAPI JSON: <http://127.0.0.1:8001/openapi.json>
- Проверка работы процесса: `GET /health` → `{"status":"ok"}`. Это liveness-проверка,
  а не проверка доступности каталога или семантической модели.

### Запрос и список кодов

```bash
curl -X POST 'http://127.0.0.1:8001/extract' \
  -H 'Content-Type: application/json' \
  -d '{
    "normalized_query": "молоток длина ручка 15 сантиметр",
    "candidate_codes": ["25.73.30.141-00000012"]
  }'
```

### Готовый JSON сервиса поиска

`POST /extract/from-search` принимает ответ сервиса поиска целиком:

```json
{
  "query": "Сапог",
  "canonical_query": "Сапог",
  "lemmatized_query": "сапог",
  "candidates": [
    {
      "ktru_code": "15.20.11.113-00000015",
      "name": "Сапоги резиновые формовые",
      "status": "ACTIVE",
      "okpd2_code": "15.20.11.113",
      "rrf_score": 0.01639344262295082
    }
  ]
}
```

Обязательны `lemmatized_query`, `candidates` и `ktru_code` у каждого кандидата.
Экстрактор не обращается к сервису поиска по HTTP: клиент передаёт уже полученный
ответ. Метаданные поиска принимаются, но в результат не копируются. Сопоставление
использует лемматизированную строку и коды, сохраняя исходный порядок среди отобранных кандидатов.
Структура ответа обоих маршрутов совпадает с результатом Python-функции ниже.

Ошибки структуры запроса дают HTTP `422`. Недоступность каталога или ресурсов
настроенной модели — HTTP `503`. Отсутствующие коды КТРУ возвращаются в
`unknown_candidate_codes` с HTTP `200`, пустая выборка допустима.

### Настройки сервера

- `CHARS_EXTRACTOR_DB_PATH` — необязательный путь к базе; по умолчанию используется
  `ktru.db` в корне репозитория независимо от рабочей директории. Для собственной
  базы удобно задавать абсолютный путь.
- `CHARS_EXTRACTOR_SEMANTIC_MODEL` — необязательное имя или локальный путь модели.
  Требует `uv sync --locked --extra semantic` и запуска через
  `uv run --extra semantic uvicorn service:app --port 8001`. По умолчанию нейросеть
  не используется и не загружается.
- `CORS_ORIGINS` в начале `service.py` — разрешённые адреса браузерного клиента.
  По умолчанию это `localhost` и `127.0.0.1` на портах `5173` и `4173`.

Например, запуск с другой базой:

```bash
CHARS_EXTRACTOR_DB_PATH=/absolute/path/ktru.db \
  uv run --no-dev uvicorn service:app --port 8001
```

Путь к базе и модель настраиваются на сервере, а не через тело HTTP-запроса.

## CLI и тесты

Из корня репозитория:

```bash
cd chars_extractor
uv sync --locked
uv run python chars_extractor.py \
  'молоток длина ручка 15 сантиметр' \
  25.73.30.141-00000012
uv run python -m unittest discover -s tests -v
```

База по умолчанию — `../ktru.db`, путь вычисляется относительно файла модуля,
а не рабочей директории. Для другой базы есть `--db /path/to/ktru.db`.
Нужна актуальная схема репозитория: `ktru_position`, `ktru_characteristic`,
`ktru_characteristic_value`. Соединение открывается в режиме `mode=ro`,
импорт, миграции и перестроение индексов не выполняются.

## Python API

При импорте из корня репозитория (в окружении с зависимостями подпроекта):

```python
from chars_extractor import extract_characteristics

result = extract_characteristics(
    normalized_query="молоток длина ручка 15 сантиметр",
    candidate_codes=["25.73.30.141-00000012"],
    # db_path="/path/to/ktru.db",  # необязательно
)
```

Возвращается обычный `dict`, совместимый с `json.dumps(..., ensure_ascii=False)`.
Функция читает характеристики **только указанных кодов**. Порядок кандидатов
сохраняется, повторные коды удаляются. Неизвестные коды попадают в
`unknown_candidate_codes`; пустой список кандидатов допустим. Отсутствующая
база вызывает ошибку SQLite, новый файл базы не создаётся.

## Формат результата

- `query` — входная строка.
- `chars` — характеристики **товара из запроса**, приведённые к структуре КТРУ.
- `candidates` — кандидаты с подтверждённым полным или частичным совпадением
  и без явно противоречащих значений.
- `rejected_candidates` — исключённые товары: код, название, статус и причины в `matches`.
- `unknown_candidate_codes` — коды, которых нет в базе.
- `unrecognized` — неразобранные фрагменты и ошибки разбора с причиной и позицией.

`chars[]` теперь имеет ту же основную структуру, что и `candidates[].characteristics[]`:
`id`, `code`, `name`, `ktru_type`, `kind`, `is_required`, `choice_type`, `values`, `issues`.
Это изменение контракта API: тип и значение требования читаются из `chars[].values[]`.
В `chars` попадают только указанные пользователем требования, а не все свойства каталога.

Например, фрагмент характеристики для запроса «молоток строительный ручка 10 см»:

```json
{
  "id": null,
  "code": "cc742fbb-8",
  "name": "Длина рукоятки",
  "ktru_type": 2,
  "kind": 2,
  "is_required": 0,
  "choice_type": 2,
  "values": [
    {"name": "Длина рукоятки", "type": "number", "value": 100, "unit": "мм", "value_code": null}
  ],
  "issues": [],
  "mapping_status": "mapped",
  "in_ktru": true
}
```

Число `10 см` пересчитывается в `100 мм` **в самом ответе**. Оно не заменяется
допустимым интервалом КТРУ `[100, 150)`: это конкретное требование пользователя.
«Масса 1500 г» становится «Масса молотка», `1.5 кг`. У интервала пересчитываются
обе границы с сохранением включённости. Строка получает написание из КТРУ,
если её значение совпадает по леммам/словарю с допустимым значением.

Дополнительные поля `chars[]`:

- `mapping_status`: `mapped` — найдено однозначное соответствие;
  `alternatives` — неявное значение может относиться к нескольким полям КТРУ;
  `not_found` — свойства нет у переданных кандидатов; `ambiguous` — требуется
  уточнение названия или единицы; `unit_mismatch` — несовместимые размерности.
- `in_ktru` — найдено ли соответствующее название **среди переданных кандидатов**.
  Это не проверка всего каталога и не утверждение о допустимости значения.
- `ktru_refs` — ссылки на реальные строки характеристик: `candidate_code`,
  `characteristic_id`, `code`, `name`. У требования пользователя `id: null`;
  общие метаданные берутся из найденных определений, при расхождении — `null`.
  `value_code: null` означает запрошенное значение без собственной строки в базе.
- `source`, `start`, `end` — фрагмент и позиции во входной нормализованной строке.
- `negated`, `unit_inferred`, `reason` — отрицание, наследование единицы и пояснение.
- `match_mode`: `single` — конкретная характеристика; `any` — достаточно совпадения
  хотя бы с одним из полей `ktru_refs` для неявного положительного требования.

Свойства, которых нет в выборке КТРУ, остаются в `chars`: например,
«водостойкость высокая» с `mapping_status: "not_found"`, `in_ktru: false`,
`code: null`, исходным значением в `values` и пустым `ktru_refs`.
«Строительный» трактуется как назначение. У приведённых молотков поля «Назначение»
нет, поэтому оно помечается `not_found`, а не подменяется одним из значений «Тип».
Остатки, которые нельзя уверенно разобрать как характеристику, сохраняются в `unrecognized`.

У каждого кандидата:

- `characteristics` содержит исходные `id`, `code`, `name`, `ktru_type`, `kind`,
  `is_required`, `choice_type`, массив унифицированных `values` и `issues`.
  Несколько допустимых значений остаются отдельными альтернативами. `ktru_type`
  — исходный числовой признак КТРУ, а `values[].type` — `number`, `string`, `interval`.
- `matches` ссылается на `chars` через `query_index`, а на характеристику кандидата
  через `characteristic_id`. `method` описывает способ сопоставления названия.

### Одинаковые значения в разных полях и дубликаты

Для «перчатка нейлон» значение «Нейлон» разрешено как в основном, так и в
дополнительном сырье. Это два разных свойства. Пользователь не указал роль сырья,
поэтому `chars` содержит одно требование «материал — Нейлон»,
`mapping_status: "alternatives"`, `match_mode: "any"` и ссылки на оба поля.
Общий `code` остаётся `null`: единого кода КТРУ для этих двух полей нет.
У кандидата достаточно совпадения хотя бы с одним полем; проверенные совпадения
перечисляются в `matches[].matched_characteristic_ids`.
Это допустимость нейлона в описании КТРУ, а не доказательство фактического состава
конкретной поставляемой пары перчаток.

В приведённой выборке остаются четыре трикотажных кандидата
`14.12.30.150-00000002`, `…00000003`, `…00000001`, `…00000004` в исходном порядке.
У шести хирургических кандидатов в этой базе характеристики отсутствуют,
поэтому они попадают в `rejected_candidates` с `not_found` в `matches`.
Явное «основное сырье нейлон» проверяет только основное сырьё;
«дополнительное сырье нейлон» — только дополнительное. Неуказанный компонент
у числового свойства и неоднозначное отрицание по-прежнему требуют уточнения.

Повторные строки одной характеристики объединяются при чтении **внутри одного товара**,
по коду, нормализованному названию и исходному типу КТРУ. Разные коды/типы не склеиваются.
Допустимые значения объединяются без повторов и без заполнения разрывов диапазонов.
`source_ids` хранит идентификаторы исходных строк, а `value_codes` — разные исходные
коды одинакового значения. `ktru_refs` сохраняет ссылки на все исходные строки.
При расхождении служебных метаданных дубликатов общее поле получает `null`.
Одинаковые характеристики у разных товаров остаются независимыми;
основное и дополнительное сырьё не объединяются. База не модифицируется.

Статусы отдельных сопоставлений:

| Статус | Значение |
| --- | --- |
| `matched` | Значение подходит |
| `value_mismatch` | Название найдено, значение не подходит |
| `unit_mismatch` | Несовместимые размерности |
| `partial_match` | Запрошенный интервал покрыт допустимыми значениями лишь частично |
| `not_found` | Характеристика не найдена у этого кандидата |
| `ambiguous` | Несколько возможных характеристик или неоднозначная единица |
| `not_comparable` | В КТРУ нет значений или есть некорректные границы |

Правила отбора в `candidates`:

- `matched` — все извлечённые требования подтверждены, неразобранных фрагментов нет.
- `partial_match` — есть хотя бы одно полное/частичное совпадение, но остаются
  неизвестные свойства, неоднозначность, неразобранный текст или неполное покрытие диапазона.
- `no_constraints` — запрос не содержит требований, возвращается исходная выборка.
- Любой `value_mismatch` или `unit_mismatch` исключает товар, даже если остальные
  свойства подходят. Он попадает в `rejected_candidates` со статусом `mismatch`.
- Если требования есть, но подтверждённых совпадений нет, товар исключается
  со статусом `undetermined`. При отсутствии результатов `candidates` остаётся пустым.

В выборке из десяти молотков из примера у всех допустимы `100 мм` длины рукоятки
и `1.5 кг` массы. Поэтому эти условия сами по себе не сокращают список.
«Молоток плотничный ручка 10 см» оставляет только `25.73.30.141-00000009`:
остальные исключаются по характеристике «Тип». Исходный поисковый порядок сохраняется;
новые товары из базы не добавляются, оценка сходства не выдумывается.

## Сравнение значений

1. Коды и имена единиц ОКЕИ приводятся к общему написанию. Числа сравниваются
   через `Decimal` после перевода в базовые единицы размерности.
2. `15 см = 150 мм`: число **не входит** в `[100, 150)`, но входит в `[150, 200)`.
   Ноль, отрицательные числа, десятичные дроби и односторонние интервалы поддерживаются.
3. Для интервала запроса требуется полное покрытие объединением допустимых
   значений кандидата. Пересечение возвращает `partial_match`, разрыв не закрывается
   искусственно. Это проверка покрытия диапазона, а не утверждение, что любое
   пересечение полностью удовлетворяет требованию.
4. Если единица в запросе отсутствует, она наследуется только при одной общей
   единице у числовых альтернатив характеристики. Это явно отмечено в
   `unit_inferred`; при разных единицах требуется уточнение.
5. Строки сравниваются по леммам и небольшому словарю синонимов. Проверка
   `не резина` означает наличие хотя бы одного разрешённого строкового значения,
   отличного от резины; это не утверждение о фактически поставляемом экземпляре.
6. Неизвестные единицы сохраняются, не превращаясь в безразмерные числа.

## Разбор текста и ограничения

Базовый режим — правила, морфология и словарь, ограниченный характеристиками
переданных кандидатов. Поддерживаются явные свойства (`длина ручка 15 см`),
сокращённые измерения детали (`ручка 10 см`, если числовое свойство однозначно),
перестановка слов в названии, количественные ограничения (`не менее`, `не более`,
`>`, `>=`, `<`, `<=`, `от … до …`, `10–15 см`), строковые значения,
неявные материалы/цвета/формы (`деревянный ручка`, `круглый боек`) и булевы
свойства (`без капюшон`, если у характеристики есть значения «Да»/«Нет»).

Словари можно расширять в `language.py`, единицы — в `values.py`.
«Прорезиненный» относится к покрытию, а не автоматически к материалу всей детали.
Правила не являются универсальным пониманием свободного русского текста:
сложные перечисления, альтернативы через «или», отсылки и произвольные неявные
свойства требуют расширения грамматики. Нераспознанный текст возвращается
в результате; неоднозначное название не выбирается по порядку в базе.

На входе необходимо сохранять порядок слов, единицы, отрицания, дефисы диапазонов
и знаки сравнения. Если нормализация уже превратила `10–15` в `10 15` или удалила
`<`, восстановить исходное условие невозможно. Эта функция не изменяет
существующий нормализатор проекта.

## Необязательный семантический режим

```bash
uv sync --locked --extra semantic
uv run --extra semantic python chars_extractor.py \
  'молоток длина ручка 15 сантиметр' 25.73.30.141-00000012 \
  --semantic-model intfloat/multilingual-e5-small
```

В Python передайте `semantic_model="intfloat/multilingual-e5-small"` либо путь
к локальной модели Sentence Transformers. Модель загружается лениво только
при отсутствии лексического соответствия названия. Возможна первоначальная
загрузка весов из сети. Проверка чисел/диапазонов всегда остаётся детерминированной.
Модель не добавляет новые товары и не извлекает пропущенные правилами фрагменты.

`semantic_threshold=0.8` и `semantic_margin=0.05` — стартовые настройки,
которые необходимо калибровать на ваших примерах. Близкие варианты возвращаются
как `ambiguous`; сходство не является вероятностью. Автотесты базового режима
не требуют нейросети или сети; качество конкретной модели надо оценивать отдельно.
