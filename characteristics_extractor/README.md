# Characteristics Extractor

Самостоятельный Python 3.12+ сервис: получает ответ поиска, извлекает явные и
неявные характеристики через локальную модель LM Studio, приводит их к
справочнику КТРУ и обрабатывает уточнения без серверных сессий.
Кандидаты используются для построения справочника и не возвращаются в ответе.
Фильтрации товаров нет.

## Запуск

Потребуются `uv` и Python 3.12+. В LM Studio загрузите модель
`qwen/qwen3.8-27b` и включите локальный сервер на порту `1234`.
Проверьте, что `curl http://localhost:1234/v1/models` возвращает её ID.

Из корня репозитория:

```sh
cd characteristics_extractor
uv sync --locked
uv run uvicorn characteristics_extractor.app:create_app --factory --host 127.0.0.1 --port 8002
```

Готовые настройки этой машины уже записаны в `characteristics_extractor/.env`:
27B, LM Studio на `localhost:1234`, отключённый thinking и абсолютный путь к КТРУ.
HTTP-сервис и CLI автоматически читают файл при запуске — `export` и `--env-file`
не нужны. На другой машине скопируйте `.env.example` в `.env` и укажите путь к БД.

Оставьте терминал открытым. Остановка — `Ctrl+C`. Если порт `8002` занят
предыдущим экземпляром, остановите его в терминале запуска или выберите другой
порт через `--port`. После изменения кода перезапустите процесс; для разработки
можно добавить `--reload`.

В другом терминале проверьте:

```sh
curl http://127.0.0.1:8002/health
```

Ожидаемый ответ: `{"status":"ok"}`. Это проверка процесса; полноценный запрос
`/extract` также требует доступных LM Studio и SQLite.

LM Studio должен быть запущен с локальным сервером на `http://localhost:1234`.
Точный ID модели проверяется через `GET /v1/models`. Сервис не скачивает и не
переключает модели автоматически. Проверенный локальный ID 27B —
`qwen/qwen3.8-27b`; сохранённая 4B — `qwen/qwen3-vl-4b`.

`KTRU_DB_PATH` задаёт абсолютный путь к SQLite. В этом checkout по умолчанию
используется `ktru.db` в корне репозитория. При установке пакета отдельно путь
нужно указать явно. База открывается только для чтения.

- `POST http://127.0.0.1:8002/extract` — первичное извлечение и уточнения.
- `GET /health` — проверка HTTP-процесса, не готовности модели или БД.
- [Swagger UI](http://127.0.0.1:8002/docs) — интерактивные запросы через `Try it out`.
- [ReDoc](http://127.0.0.1:8002/redoc) — документация для чтения.
- [OpenAPI JSON](http://127.0.0.1:8002/openapi.json) — актуальная схема API.

## Отладочный вывод запросов

В `.env` включите:

```dotenv
EXTRACTOR_DEBUG_PRINT=true
```

После изменения флага перезапустите сервис. Вывод появляется в терминале
Uvicorn с префиксом `[EXTRACTOR DEBUG]`. Каждая запись содержит `request_id`,
событие `event` и время от начала запроса `elapsed_ms`.

Печатаются входящее тело запроса, этапы загрузки справочника и нормализации,
отправленный модели JSON, её ответ до проверки, итоговый HTTP-статус и тело
ответа клиенту. При ошибках выводятся причины, цепочка исключений и traceback;
для HTTP 422 видны поля, не прошедшие валидацию. Ошибочный ответ LM Studio
логируется до 64 КиБ. Необработанные ошибки отмечаются `http.unhandled_error`.
Заголовки авторизации не печатаются, известные поля секретов и значение
`LM_STUDIO_API_KEY` маскируются. Текст запросов и характеристики видны полностью.

Для отключения установите `EXTRACTOR_DEBUG_PRINT=false` и перезапустите сервис.
Без флага отладочный вывод выключен. Обычные access/error-логи Uvicorn управляются
отдельно. Флаг относится к HTTP-запросам; формат ответов API не меняется.

## OpenAPI

Спецификация описывает обе операции, входные и выходные модели, варианты
значений, stateless-цикл и ответы `200/409/422/502/503/504`. Для первого запроса
в Swagger есть готовый пример. У `422` описаны обе формы: стандартная ошибка
валидации с массивом `detail` и ошибка состояния с объектом `detail`.

Файл [openapi.json](openapi.json) можно импортировать в Postman или использовать
для генерации клиента. Он генерируется из приложения, а не редактируется вручную.
Обновление после изменения контракта, из папки подпроекта:

```sh
uv run python scripts/export_openapi.py
```

Для экспорта не нужны запущенный сервер, модель или база. Актуальная схема
работающего экземпляра всегда доступна по `/openapi.json`.
Настройка использует штатные механизмы
[FastAPI OpenAPI](https://fastapi.tiangolo.com/tutorial/metadata/) и
[описания дополнительных ответов](https://fastapi.tiangolo.com/advanced/additional-responses/).

## Первый запрос

Первый запрос — **неизменённый ответ поиска**, без дополнительной обёртки:

```sh
curl http://127.0.0.1:8002/extract \
  -H 'Content-Type: application/json' \
  --data-binary @examples/search_response.json
```

CLI использует тот же pipeline:

```sh
uv run python -m characteristics_extractor examples/search_response.json
uv run python -m characteristics_extractor examples/search_response.json --dry-run
uv run python -m characteristics_extractor examples/search_response.json --initial-only
```

`--dry-run` выводит payload без обращения к модели; `--initial-only` возвращает
промежуточные `facts` до нормализации. Оба режима предназначены для первичного
запроса. Обычный CLI также принимает сохранённый документ уточнений с добавленным
исходным списком `candidates`.

## Контракт

Входные `query`, `canonical_query`, `lemmatized_query`, `candidates` соответствуют
формату сервиса поиска. Полный пример с десятью кандидатами находится в
`examples/search_response.json`. `candidates` обязателен в каждом запросе,
включая уточнения. Фронт сохраняет исходный список после этапа поиска.

Ответ содержит `query`, `canonical_query`, `lemmatized_query` и поля ниже.
Поля `candidates` в ответе нет.

| Поле | Назначение |
| --- | --- |
| `schema_version` | Сейчас `1.0` |
| `search_target` | Цель поиска: краткое название товара без характеристик, например `Молоток`; `null`, если товар не указан однозначно |
| `attributes` | Извлечённые характеристики |
| `clarifications` | Вопросы по неуточнённым атрибутам |
| `issues` | Диагностика, в том числе неподдерживаемые ограничения |
| `status` | `completed` или `needs_clarification` |
| `input_fingerprint` | Контрольная сумма текста и кодов кандидатов для продолжения |

Нет `attributes` или значение `null` — первоначальное извлечение с одним
вызовом модели. Массив, в том числе `[]`, — продолжение **без вызова модели**.

Для «Молоток с рукоятью 15 см» ответ содержит `"search_target": "Молоток"`,
а длина рукоятки остаётся в `attributes`. Цель извлекается тем же вызовом модели,
что и характеристики; первый кандидат не используется как готовая цель.
Для одного названия «Молоток» цель сохраняется даже при `attributes: []`.
Если запрос содержит только «длина 15 см», модель должна вернуть
`search_target: null`. Это поле само по себе не фильтрует кандидатов и не меняет
статус уточнений.

У атрибута есть `id`, исходная цитата `source_text`, `source_span`,
`mention_type: explicit | implicit`, `original_value`, `characteristic_options`,
`characteristic_id`, `characteristic_name`, `normalized_value`, `resolution_source`.
Производные поля вычисляются сервером заново. Статусы:

- `resolved`: выбраны характеристика и нормализованное значение;
- `unknown`: `extracted_name` и точное сообщение `Неизвестная характеристика`,
  без привязки к КТРУ;
- `needs_clarification`: нужно выбрать характеристику, уточнить единицу или значение.

Неизвестная характеристика не блокирует завершение. `completed` означает,
что отсутствуют вопросы и блокирующая диагностика, а не что всё найдено в КТРУ.

Значения имеют тег `type`: `number`, `string`, `boolean`. Например, исходное
`{"type":"number","value":15,"unit":"см"}` становится
`{"type":"number","value":150,"unit":{"okei_code":"003","name":"Миллиметр"}}`,
если выбрана характеристика с единицей ОКЕИ 003. Неизвестные свойства сохраняют
только исходное значение: для них нельзя придумывать стандарт КТРУ.

`source_text` дословно взят из **исходного `query`**. `source_span` — полуинтервал
`[start, end)` в символах Python Unicode, не в байтах или JavaScript UTF-16.
Это существенно для emoji. Лемматизированный текст — вспомогательный: сервис
поиска может удалить из него отрицания и предлоги.

Поддерживается только конкретное значение. Неравенства, отрицания, диапазоны и
альтернативы (`или`) попадают в `issues` с `code: unsupported_constraint`.
`operator` и списки альтернативных значений в атрибутах запрещены схемой.
Числовые интервалы (`100-120 см`, `100–120 см`, `от 100 до 120 см`)
дополнительно распознаются в Python: даже если модель выдаёт границы как два
равенства, сервис возвращает HTTP 200, `status: needs_clarification` и
блокирующий `unsupported_constraint`. Другие конкретные характеристики
обрабатываются обычным образом. Для исправления диапазона измените запрос
и начните новый разбор (`attributes: null`).

## Stateless-уточнения на фронте

Если модель предложила характеристики разных типов товаров, сервис сначала
сопоставляет их `product_name` с `search_target` по полному названию в начальных
формах слов, независимо от регистра и порядка слов. Единственный вариант для
определённой цели выбирается автоматически: например, «Российский размер —
Брюки спортивные» для цели «Спортивные брюки». Исходные варианты сохраняются.
Если цель сокращена моделью («Шапка»), а точного совпадения с названием товара
нет, используется полное название, явно присутствующее в исходном запросе
(«Зимняя шапка»). Такой выбор допустим только при единственном подходящем
варианте; отсутствующие признаки вроде «детская» не добавляются по догадке.
Если подходящих вариантов несколько или совпадения нет, остаётся вопрос выбора.
При неоднозначном списке вариантов проверяются также определения с теми же
названиями во всём переданном справочнике: модель может пропустить вариант
для явно названного товара. Единственный восстановленный вариант добавляется
в `characteristic_options`; при нескольких подходящих определениях выбор не делается.
Уже выбранный `characteristic_id` не переопределяется. Кандидаты и их оценки
не меняются; значения характеристик товаров для такого выбора не сравниваются.

1. Сохранить ответ целиком и отдельно исходный список `candidates` из сервиса поиска.
2. Для `choose_characteristic` записать выбранный `options[].characteristic_id`
   в соответствующий атрибут. Для `specify_unit` изменить `original_value.unit`;
   для `specify_value` — `original_value` (включая корректный `type`).
3. Установить `resolution_source: user` у изменённых атрибутов.
4. Очистить `clarifications`, добавить сохранённый `candidates` и отправить документ снова на `POST /extract`.

Без `candidates` повторный запрос вернёт HTTP 422: сервис stateless и не хранит
список кандидатов между обращениями.

Поле `search_target` также возвращается целиком и сохраняется без повторного
извлечения. Для старого документа без этого поля результат будет `null`;
начните новый разбор, чтобы получить цель поиска.

Пример обработки выбора:

```javascript
const next = structuredClone(response);
next.candidates = structuredClone(searchResponse.candidates); // сохранённый ответ поиска
const attribute = next.attributes.find(a => a.id === question.attribute_id);
attribute.characteristic_id = selectedOption.characteristic_id;
attribute.resolution_source = 'user';
next.clarifications = [];
const updated = await fetch('http://127.0.0.1:8002/extract', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify(next),
}).then(r => {
  if (!r.ok) throw new Error(`Extractor HTTP ${r.status}`);
  return r.json();
});
```

Не удалять `characteristic_options` из атрибутов: именно они сохраняют варианты,
когда фронт очищает вопросы. Пропущенные ответы породят те же вопросы заново.
Выбор характеристики может привести к следующему вопросу об единице или значении.
Частичные ответы допустимы. Названия, пересчитанные значения и статус заполнять
на фронте не нужно; отправленные значения этих полей не считаются достоверными.

`input_fingerprint` надо возвращать без изменения. При изменении текста или
набора кодов кандидатов начать новый разбор: `attributes=null`,
`clarifications=[]`, `issues=[]`, `input_fingerprint=null`. Так же исправляются
ограничения из `unsupported_constraint`, не представленные атрибутом.

Сессий, подписей и токенов продолжения нет. Контрольная сумма выявляет случайную
смену контекста, но не подтверждает авторство документа. Весь документ остаётся
пользовательским вводом. Сервер проверяет ID по текущему справочнику, принадлежность
выбора переданным вариантам и заново нормализует значения. Изменение справочника,
при котором исчезли ID, требует нового разбора.

## Справочник и нормализация

КТРУ может хранить размер как текстовую характеристику. Число без единицы
автоматически приводится к единственному численно совпадающему текстовому
значению: `56` → `"56"`. Исходное значение сохраняется. Округление, выбор
интервала вроде `"54-56"` и отбрасывание явно указанной единицы не выполняются.
На этапе извлечения известная единица, придуманная моделью при отсутствии
обозначений единиц в исходном запросе, сбрасывается в `null`. Например,
модельное `56 см` для текста «размер 56» становится исходным числом `56` без
единицы. Явные единицы, их известные синонимы и неизвестная единица модели
сохраняются для обычной проверки; ответы пользователя при уточнении не исправляются
этим правилом. Исправление видно в DEBUG-событии `extraction.invented_unit_removed`.

По кодам кандидатов читаются `ktru_position`, `ktru_characteristic`,
`ktru_characteristic_value`: параметризованные запросы, `mode=ro`, `query_only`,
один снимок БД на запрос. Кандидаты без характеристик разрешены, даже если
характеристик нет у всех кандидатов. В `issues` возвращается предупреждение
`incomplete_catalog` с `blocking: false`. Указанные пользователем свойства,
которых нет в загруженном справочнике, становятся неизвестными характеристиками.
Запрос только с названием товара возвращает пустой `attributes` и `completed`.
Пустой `candidates: []` также разрешён: свойства извлекаются без справочника
и помечаются как неизвестные, в `issues` добавляется неблокирующее предупреждение.
Само поле `candidates` обязательно, в том числе при повторной отправке.
Отсутствующий в БД кандидат или некорректные данные существующих характеристик
по-прежнему блокируют разбор с HTTP 409.

Определения объединяются только при совпадении кода, названия товара, ОКПД2,
названия характеристики, типа, вида и набора единиц. Имена сравниваются с
нормализацией регистра и пробелов; синонимы автоматически не объединяются.
ID вычисляется через SHA-256. При отсутствии кода используется исходный row ID.
Источники, коды значений и диапазоны сохраняются в `CatalogContext`.
Разные товары и единицы остаются разными определениями.

Модель видит компактный справочник и короткие идентификаторы `c1`, `c2`, ….
Названия в результате и полные ID подставляет Python. Числовые диапазоны не
передаются для сравнения; ни извлечение, ни нормализатор не проверяют соответствие
товара запросу. `15 см` переводится в `150 мм`, даже если в записи кандидата
стоит другой диапазон. Коды исполнения `1`, `2`, `3` не расшифровываются догадкой.

Единицы переводятся в Python через Decimal и Pint. Словарь ОКЕИ и русских алиасов
находится в `units.py`: длина, площадь, масса, мощность, напряжение, ток, заряд,
температура, угол, обороты, штуки. Несовместимые или неизвестные единицы дают
уточнение. Для неизвестной ОКЕИ-единицы допускается только сохранение при точном
совпадении нормализованного названия. Отсутствующая исходная единица не угадывается.

Текстовые значения сверяются с официальными написаниями через pymorphy3 и небольшой
явный словарь синонимов (`стальной` → `Сталь`). Неоднозначное или отсутствующее
значение вызывает `specify_value`, а не `Неизвестная характеристика`: сама
характеристика уже известна. `suggested_values` даёт варианты для отображения.
Прорезиненное покрытие не считается доказательством материала всей рукоятки.

## LM Studio и ошибки

`.env` загружается автоматически при создании HTTP-приложения и запуске CLI.
В этом checkout файл ищется в папке подпроекта независимо от рабочей директории.
Для отдельно установленного пакета используется `.env` в текущей директории.
Явно заданные переменные окружения имеют приоритет над файлом. После изменения
`.env` перезапустите процесс. Файл исключён из Git; `.env.example` — шаблон для
других разработчиков. Загрузка реализована через
[python-dotenv](https://bbc2.github.io/python-dotenv/).

Настройки:

| Переменная | По умолчанию |
| --- | --- |
| `LM_STUDIO_MODEL` | Обязательный точный ID |
| `LM_STUDIO_BASE_URL` | `http://localhost:1234/v1` |
| `LM_STUDIO_REASONING_EFFORT` | Не передаётся; для локальной 27B установить `none` |
| `LM_STUDIO_API_KEY` | Не задан |
| `LM_STUDIO_TIMEOUT_SECONDS` | `120`, полный срок запроса |
| `LM_STUDIO_CONNECT_TIMEOUT_SECONDS` | `5` |
| `LM_STUDIO_MAX_TOKENS` | `2048` |
| `LM_STUDIO_TEMPERATURE` / `TOP_P` / `TOP_K` | `0.7` / `0.8` / `20` |
| `LM_STUDIO_PRESENCE_PENALTY` / `REPEAT_PENALTY` | `1.5` / `1.0` |
| `LM_STUDIO_MAX_RESPONSE_BYTES` | `1000000` |
| `LM_STUDIO_MAX_PROMPT_CHARS` | `100000`, включая схему |
| `EXTRACTOR_CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` |

Для колонок sampling сокращены имена: каждая переменная начинается с
`LM_STUDIO_`. Это начальные настройки, не оценка качества модели.

На локальной MLX 4bit сборке `qwen/qwen3.8-27b` проверено: без
`reasoning_effort: none` структурированный JSON попадал в `reasoning_content`,
а `content` оставался пустым. `chat_template_kwargs.enable_thinking=false` не
помогал. С `reasoning_effort: none` JSON возвращается в `content`. Значение `off`
этот endpoint отклоняет. Настройка зависит от версии LM Studio и модели.

Клиент использует [JSON Schema Structured Output LM Studio](https://lmstudio.ai/docs/developer/openai-compat/structured-output)
и строгую Pydantic-валидацию. Один вызов, без автоматических повторов; конечный
тайм-аут и лимит токенов. Ответ с `finish_reason: length`, пустым `content`,
Markdown, рассуждениями, выдуманными ID или цитатами отклоняется. Отдельное поле
рассуждений никогда не подменяет финальный ответ. При отмене ожидания соединение
закрывается; фактическая остановка генерации зависит от LM Studio.

| HTTP | Причина |
| --- | --- |
| 409 | Неполный справочник; `detail.issues` содержит причины |
| 422 | Невалидный вход или состояние уточнения |
| 502 | Некорректный, обрезанный или слишком большой ответ LLM |
| 503 | Недоступность LM Studio/БД или ошибка конфигурации модели |
| 504 | Тайм-аут LLM |

Для бизнес-уточнения возвращается **200**, `status: needs_clarification`.
При блокирующем `unsupported_constraint` массив вопросов может быть пустым:
фронт должен также показывать `issues`, предлагая изменить текст запроса.

## Проверки

```sh
uv run python -m unittest discover -s tests -v
```

При работающих сервисе и LM Studio — шесть реальных запросов (занимают несколько
минут), включая уточнение без ответа и последующий выбор:

```sh
uv run python scripts/smoke_test.py --url http://127.0.0.1:8002
```

Этот скрипт использует фиксированных кандидатов из примера; лемматизация тестовых
фраз заменена приведением регистра, чтобы проверять именно этот сервис.

Автоматические тесты не требуют LM Studio/GPU или реального КТРУ: временная SQLite
для репозитория, MockTransport для модели, ASGITransport для HTTP. Проверяются
чтение одним снимком без записи, построение справочника, ограничения генерации,
цитаты, ID, конвертации и несколько циклов уточнений на разных экземплярах сервиса.

Структура JSON, валидные ссылки и единицы не доказывают полноту извлечения или
правильность семантики модели. Для оценки качества нужна размеченная выборка
запросов; единичный интеграционный прогон её не заменяет.

Результаты выполненного прогона 27B: [SMOKE_RESULTS.md](examples/SMOKE_RESULTS.md).
